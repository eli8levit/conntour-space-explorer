Space Explorer how it works
PLATE 00 How Space Explorer works

Search 100 NASA photos in plain English, with a score you can trust and a map of where each was taken.

A React app talks to a FastAPI backend through nginx. One Postgres database holds the images, a vector for each image, and every search you ran. A small text model runs inside the backend, so search needs no outside service.

100NASA images
1SQL query per search
0.83P@5, hybrid search
384numbers per vector

The whole app in 30 seconds

  1. Browse: all 100 photos on one dark canvas, loaded in one request from /api/sources.
  2. Search: keyword search and meaning search run in one SQL query. Python blends them into one score: 80% meaning, 20% words.
  3. History: every search is saved with a snapshot of its results. Reopening never re-runs it.
  4. Where in space: a lazy-loaded 3D map puts each photo on Earth, in orbit, on Mars or in deep space.

The stack

  • Frontend: Vite, React 18, TypeScript, Tailwind, TanStack Query, react-router, react-three-fiber
  • Backend: FastAPI, async SQLAlchemy + asyncpg, Pydantic, fastembed (all-MiniLM-L6-v2, ONNX)
  • Data: Postgres 16 with pgvector
  • Infra: Docker Compose, nginx, uv, a Cloudflare Worker in front of one VM
PLATE 01 The assignment

Four requirements, four answers

The brief asked for browsing, natural-language search with a confidence score, search history with delete and pagination, and one special feature. The given stack: FastAPI, async SQLAlchemy, PostgreSQL, React, TypeScript, Tailwind, Docker Compose, nginx and uv.

Req 1 · Browse

The archive canvas

All 100 photos at once, oldest first, with plate numbers. Drag to pan. Click for full metadata at ?image=<id>.

Req 2 · Search

Hybrid search + confidence

Full-text plus vectors. Each result shows a %, a meaning/words breakdown and a "why it matched" line.

Req 3 · History

Snapshots, keyset pages

Stored results, 10 per page with an opaque cursor, delete with 6 seconds to undo.

Req 4 · Special

"Where in space"

A 3D line-art map of where each photo was taken, linked to search results.

Bonus items done: year filtering (?from=&to=), pagination (keyset + offset), keyword-only fallback if the model fails, keyboard shortcuts (/, ↑↓, ←→, Esc).

PLATE 04 Hybrid retrieval and the confidence score

    
Two searches in one query, one number at the end

    
Keyword search finds exact words and IDs like "STS-135", but it can't find "red planet". Meaning search finds "red planet", but its top 5 is noisier. So one SQL query asks both, merges the candidates, and Python turns the two raw scores into one confidence.

  


  

    
Retrieval: one SQL round trip
backend/repositories/search.py · HYBRID_CANDIDATES_SQL

    

    
    

    
Why OR: plainto_tsquery ANDs the words, so "images of Mars rovers" would need every word. A row found by only one side still gets the other side's score, which is what makes the blend fair.

Why stretch the cosine
Raw cosine is a bad confidence. Unrelated captions still score about 0.2, and good matches reach 0.6 to 0.8. So 0.20–0.70 is stretched to 0–1. Until Nov 9 the top was 0.50; plate 05 says why that changed.

    
Why "found / total"
The OR query lets one word match. Without coverage, "solar flares" would give full word credit to "Parker Solar Probe". With it, Parker gets half.

    
Why id_rule is stored
The ID rule changes the score after the blend, so the meaning and words shown no longer add up to the score on screen. Each hit keeps id_rule (raised / halved / null) so the UI can explain it.

The Nov 9 fix: are the orange results right?
backend/config.py · commit 8d4b9f0

    

      

        
P@5 and recall don't say whether the orange results are right, so the eval got a new metric, relevant among strong. With the old constants only 30% of strong results were relevant.

        
The cause: any cosine of 0.50 or more counted as "Meaning 100%". A real rover photo (0.67) and an orbital Mars photo with no rover (0.55) looked identical, so the model's difference was thrown away.

        
The fix: the ceiling went from 0.50 to 0.70, and the minimum from 0.20 to 0.12 to keep recall. Floor, 80/20, the 0.5 strong line and both guard rules didn't change.

The known limits

      
"mars rover" is read as mostly "Mars". Cosine of "mars rover" with "mars" is 0.74. So 3 of the 7 strong results are orbital photos with no rover: Lycus Sulci 61%, Ganges Chasma 56%, Ophir Chasma 51%. Flip to Keywords and they drop to about 22%.

      
"red planet" stays faint: 9 results, none strong, best Lycus Sulci 25%. MiniLM gives it the same cosine (0.359) as "solar flares" → Parker Solar Probe.

      
Next: a rule that partial matches of a multi-word query can't be strong, or a cross-encoder re-ranker on the top 20.

Key choices

      
    
        
  • search_vector is generated. Title has weight A, keywords B, description C, so a title word ranks higher. Generated columns need IMMUTABLE functions and array_to_string is only STABLE, so db/schema.py adds a tiny immutable_array_to_string wrapper.
    • 
        
  • Place columns are flat on sources, not a table. Each image has exactly one place.
    • 
        
  • embedding is NULL until the seed fills it. Such a row is keyword-only.
    • 
        
  • No Alembic. create_all plus idempotent ALTER … ADD COLUMN IF NOT EXISTS for later columns (id_rule, short_title, credit).

PLATE 07 Backend layers

    
HTTP, logic and SQL each live in one place

    
The scaffold had controllers → repositories → db. I kept that and added services/ for logic that is neither HTTP nor SQL. A request goes down the stack; a Pydantic model comes back up. Nothing above the repositories knows SQLAlchemy exists.

  

  

    

    

      
      
controllers/HTTP only
Routes, params, status codes
Validates with Pydantic, maps errors to 400/404/422. dependencies.py injects the embedder so tests can swap it.

      
services/logic
The search use case
search.py orchestrates, scoring.py is pure math, embedding.py wraps the model, cursor.py encodes history cursors.

      
repositories/all SQL
Queries in, Pydantic out
source.py browse + places, search.py the hybrid query, history.py create / page / get / delete.

      
db/engine
Models, async session, schema
SQLAlchemy models, asyncpg engine, and schema.py that is safe to run on every start.

Snapshots, keyset pages, and an undo that never touches the server

    
Every search is stored with its results, so reopening shows exactly what you saw, even after the model or constants change. The list pages with a cursor instead of an offset. Run the demo below to see why.

      PLATE 10 The special feature
      
    
      "Where in space": a map of where each photo was taken
      
    
      The captions hide a lot of place data: Mars coordinates, launch pads, "taken from the ISS". The scene puts every image on Earth, in orbit, on Mars or in deep space. From a results page, "See these in space →" lights your strong matches orange and faint ones white.
      
  
      

  
      
    
      1 · Rules draft
      build_places.py
      Mars lat/lon from the caption (0–360 E → ±180), ISS and Shuttle photo-ID patterns, the location field, named sites, NASA center as last resort.
      
    
      2 · Hand review
      All 100 checked
      27 entries changed. A storm photo belongs off New England, not at Goddard which published it.
      
    
      3 · Provenance
      How we know
      caption 58 · location field 30 · manual 8 · NASA center (approx.) 4. The card says it in words.
      
    
      4 · Load
      places.json → seed
      Applied by nasa_id on every start. test_places.py checks one valid place per image.
      
  
      

  
      
    
      
      
      
      frames drawn 0drifting
      
      
      
        
        
        
        
      
      
    
      
    
      
      
      Pins are one THREE.Points cloud. Each pin is one vertex, drawn as a small square. Pins, cluster markers and leader lines are 3 draw calls, not 100 meshes.
      
      
      Render on demand (frameloop="demand"). Turn off Drift: the frame counter stops. Values that change every frame live in refs, not React state.
      
      
      HTML labels by projection. Each frame projects 3D anchors to pixels and moves divs with a CSS transform. Labels, click picking (12 px, 24 px on touch) and pins share one projection, so they always agree.
      
      
      Clusters within 2.5° (about 280 km). Kennedy alone has about 40 photos. A click fans them out on a sunflower spiral (golden angle) with a line back to each true spot.
      
      
      Not to scale, on purpose. Planet sizes keep their real ratio and the rings keep real inclinations (ISS 51.6°, Shuttle 28.5°). Distances are shortened or Mars would be a dot.
      
      
      This globe is a 2D canvas sketch of the idea. Pin positions are approximate and only the Kennedy count comes from the docs.

      PLATE 12 Decisions and trade-offs
      
    
      Every choice has a cost
      
    
      Open a row to see what each choice gave up. Below it: what changes at scale.
      
  
      
  
      
  
      
    
      At 1M images I would…
      
    
      
      
        
        
      • Keep and tune the indexes. GIN and HNSW already exist. HNSW returns at most hnsw.ef_search rows (default 40); the code already raises it per transaction to the 200 pool.
        • 
        
      • Add a cross-encoder re-ranker on the top 20. This fixes "red planet" and close STS neighbours.
        • 
        
      • Cache query embeddings (LRU or Redis by normalized query).
        • 
        
      • Embed on ingest via a queue, not all at startup.
        • 
      
      
      
        
        
      • Alembic for reviewed, versioned migrations.
        • 
        
      • Auth: owner_id on searches; filter every history query and delete.
        • 
        
      • Page the archive (keyset or viewport tiles), estimate the history count, server-side clusters for /api/places.
        • 
        
      • Observability: latency, keyword-only rate, "no strong match" rate as a quality signal.
